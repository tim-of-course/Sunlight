## Attempt with cross-process mutation queue

Build: release `sun.exe` SHA-256 `98269e9c272a2d14c6d4c40c6e014f27b0467e256315165cebd71e3994afb56b`, source commit `7a7ed0dbaa0ac41d06248ea0bde2c40284faf098` plus the tested uncommitted worktree.

Result: **fail** during the first four concurrent `topic_create` calls. The OS-owned repository mutation queue prevented a stale-state race, but one serialized state transaction held the queue long enough for another process to reach the frozen 10-second maximum:

```json
{
  "code": "repository_writer_busy",
  "message": "timed out waiting for another MCP writer in this repository",
  "details": {
    "timeout_ms": 10000,
    "transport": {
      "automatic_concurrency_retries": 0,
      "queue_ms": 10005,
      "worker_ms": 0
    }
  }
}
```

The test began at `2026-07-23T22:42:18.523Z`; four release MCP processes began after ingestion at approximately `22:44:23Z`; the bounded failure was written at approximately `22:44:57Z`. The disposable repository was removed by the harness. The source Phaser worktree remained clean at the same commit, its remote was never changed, and the disposable clone had its remote removed before Sunlight use. No commit, export, or push occurred.

Diagnosis: the queue worked as designed, but `RealRepoState::load` read identical content-addressed blobs repeatedly through `entries`, `base_entries`, projections, operations, and checkpoints, while `persist_blobs` revalidated the same hash once for every duplicate reference. A metadata-only topic creation therefore performed repository-sized repeated blob I/O while holding the mutation queue. The follow-up implementation adds one per-load content-hash cache and deduplicates blob persistence by hash without changing the durable state schema or correctness boundary. The final OA-07 run must use a new release build and retain its own JSON evidence; this failed attempt is not averaged into a later pass.

Result: **fail** at the same first four-author topic-creation burst. The bounded error remained honest and changed only slightly to `queue_ms: 10002`, `worker_ms: 0`, `automatic_concurrency_retries: 0`.

This disproved the narrower duplicate-reference diagnosis as sufficient. A save still performed two repository-sized operations while holding the queue: `persist_blob` reopened and compared every already-loaded blob, and the publication-sequence CAS called full `RealRepoState::load_from_path`, reopening all blobs solely to read one integer. The next follow-up makes sequence CAS metadata-only and verifies object integrity when a blob enters memory, allowing already-present content-addressed objects to remain immutable without rereading them on every unrelated metadata publication. A focused corruption test proves that the next state load rejects a tampered blob and retains recovery evidence.

Build: release `sun.exe` SHA-256 `ff7d4a2f68553fc9629daaeb2a0d20312bc87d97378ae76c30d8416441b55287`.

The final-run variability therefore still made the frozen 10-second maximum unsafe and exceeded the 2-second mutation threshold even when correctness succeeded.

The diagnosis shifted from save duplication to eager content loading for metadata-only operations. The next implementation adds an explicit metadata-only state-loading mode, preserves missing-object checks during publication, and retains full hash verification whenever content bytes enter memory. Focused tests prove that a metadata-only publication preserves exact blob bytes and that full loading rejects tampered content-addressed data.

A four-process retained diagnostic with the metadata-only release build (`c8b131e0d97b08c6d2b9f0d8906653acb995af6fffa999b366afbde016a5a853`) produced four successful topic creations with **233–237 ms worker time**, **0–730 ms queue time**, **247–999 ms external completion time**, and zero retries.
